# Working on this project

This dashboard auto-publishes on every push to `main` and auto-commits fresh data twice a
weekday. That's convenient, but it means `main` is live the moment you push. These are the
habits that keep it safe to move fast.

## Commit frequently, in small pieces

Make one commit per logical change (one chart added, one scoring fix, one copy edit) instead of
batching unrelated changes together. Small commits are what make reverting cheap: if something
looks wrong on the site, `git log --oneline` should make it obvious which commit to blame and
`git revert <sha>` undoes just that change without touching anything else.

```bash
git add pipeline/universe.py
git commit -m "Add SOFR futures curve to the liquidity group"
git push
```

Avoid `git commit -a -m "updates"` covering five unrelated files — it works today and becomes a
guessing game the day you need to undo one piece of it.

## How to undo something

- **A bad commit on `main`**: `git revert <sha>` and push. This creates a new commit that undoes
  the change, so history stays intact and the site redeploys automatically. Prefer this over
  `git reset` on a branch other people (or the bot) are also pushing to.
- **A bad automated data refresh**: the bot's commits are always named `data: refresh <timestamp>`
  and only ever touch `site/data.json`, so they're always safe to revert individually —
  `git revert <data-commit-sha>` — without affecting your own edits.
- **Uncommitted local changes you want to throw away**: `git status` first to see what's there,
  then `git checkout -- <file>` (or `git restore <file>`) for a single file, or `git stash` if you
  might want them back later.
- **You're not sure what changed recently**: `git log -p -- <path>` shows the actual diffs over
  time for one file; `git blame <file>` shows which commit touched each line.

## Branching for anything non-trivial

For a quick copy fix (`site/notes.json`) or a one-line tweak, committing straight to `main` is
fine — that's the whole point of the auto-deploy. For anything larger (a new scoring rule, a
redesign of a section, adding a batch of new chart series), work on a branch and open a PR:

```bash
git checkout -b add-japan-sector-charts
# make changes, commit as you go
git push -u origin add-japan-sector-charts
# open a PR into main, review the diff, then merge
```

This gives you a chance to look at the full diff before it goes live, and keeps `main`'s history
readable — each merged PR is one reviewable unit, even if it contains several small commits.

## Tag before big changes

Before a redesign or a change to how scores are computed, tag the last known-good commit so it's
a one-line `git checkout <tag>` to compare against or roll back to, rather than scrolling through
`git log`:

```bash
git tag pre-redesign-2026-09
git push origin pre-redesign-2026-09
```

## What's safe to hand-edit vs. generated

| File | Hand-edit? |
|---|---|
| `site/notes.json` | **Yes** — this is the written read and trade ideas. Edit freely, commit, push. |
| `pipeline/universe.py` | **Yes** — this is the chart list. Add/remove/reclassify series here. |
| `pipeline/fetch.py` | **Yes** — the scoring and fetch logic. |
| `site/index.html` | **Yes** — the page itself. |
| `site/data.json` | **No** — regenerated by `pipeline/fetch.py` every run. Hand edits will be overwritten by the next scheduled refresh (twice per weekday). |
| `_site/` | **No** — build output from `pipeline/build_site.py`, gitignored. |

## Before pushing a pipeline change

Run it locally first so a typo doesn't silently break the next scheduled refresh:

```bash
pip install -r pipeline/requirements.txt
python pipeline/fetch.py            # writes site/data.json
python pipeline/build_site.py       # writes _site/, sanity-check it opens correctly
cd _site && python -m http.server   # eyeball it before pushing
```

## Secrets

Never commit an API key (e.g. `FRED_API_KEY`) into any file. It belongs in
**Settings → Secrets and variables → Actions** as a repo secret, referenced in the workflow as
`${{ secrets.FRED_API_KEY }}`. If a key ever ends up in a commit, rotate it immediately — removing
it from a later commit does not remove it from history.
